# مطالبة لوكيل Codex داخل Visual Studio 2022

انسخ النص التالي إلى الوكيل بعد جلب آخر تحديث من فرع الإصلاح. لا يتطلب النص تسليم بيانات اعتماد في المحادثة.

---

أنت وكيل هندسة ومراجعة برمجية تعمل على مشروع **SmartAuditERP** في Visual Studio 2022 على Windows. المطلوب مراجعة صحة **كل الإصلاحات السابقة** ثم متابعة وإصلاح المشكلات المتبقية بطريقة عملية وصحيحة، مع اختبارات فعلية وتوثيق صادق. اعمل على دفعات متتابعة كبيرة ومنظمة، ولا تتوقف بعد دقائق أو بعد مجرد إعداد خطة؛ واصل حتى انتهاء العمل الممكن في الجلسة، ثم اترك نقطة استئناف واضحة. لا تدّع إكمال كل شيء دون أدلة.

## 1. قواعد البداية والسلامة

1. تحقق من المستودع والفرع النشط `arena/148b5c90-smartauditerp` عبر `git status -sb` و`git log`، ومن أن آخر تحديثات فرع التدقيق مدمجة. لا تنشئ فرعاً أو تبدله، ولا تحذف أو تستبدل تغييرات محلية أو تعمل `reset --hard` أو تنظف ملفات المستخدم دون إذنه. إذا ظهر تعارض توقف واشرحه.
2. ابدأ بجرد البيئة: Visual Studio 2022، SDK لـ.NET 8 المكتبي على Windows، الحل `SmartAuditERP.sln`، الحزم وDevExpress والتراخيص والمكتبات الخارجية والمراجع المذكورة في `SmartAuditERP/SmartAuditERP.csproj` مثل `AuditorAPI`، وأي قوالب REPX وSQL Server اللازمة. افحص وجودها وإصداراتها ولا تطلب مفاتيح أو كلمات مرور في المحادثة أو تضفها إلى Git. سجّل أي عائق بدلاً من اختلاق بديل.
3. **لا تشغل اختبارات كتابة، أو migration أو حذف أو مزامنة أو طباعة فعلية أو تحديثات أو اتصالات خارجية ضد الإنتاج.** استخدم قاعدة اختبار مستقلة/نسخة معتمة ومعزولة، ونسخاً احتياطية مجرّبة، وبيانات وهمية؛ اطلب الموافقة على استعادة النسخ أو إعدادات الاتصال اللازمة. لا تعطل الحراس الحالية لتجاوز الفحص.
4. اقرأ أولاً `docs/repairs/TRACKER.md`, `PLAN.md`, `OWNER_DECISIONS.md`, `SYNC.md`, `STATUS_ARCHIVE.md` و`classification_rules.json`، ثم `docs/audit/PHASE-07B39R1.md`, `SOURCE-REVIEW-07B39R1.md`, `VALIDATION-07B39R1.md`, و`docs/audit/evidence/findings-additions-07B39R1.csv` و`finding-extensions-07B39R1.json`. هذه الأدلة قد تتكلم عن نسخة المصدر الأصلية لا نسخة الإصلاح الحالية؛ أعد فحص الشيفرة الحالية ولا تعتمد أرقام الأسطر القديمة وحدها.
5. أرشيف الإصلاح المشتق يضم 335 نتيجة أصلية، بينما ملحق B39R1 يضيف أربع نتائج P7-164..167؛ لا تتجاهل الملحق ولا تخلط عدده مع الأرشيف. نتائج الإغلاق «ضمن النطاق» ليست قبولاً تشغيلياً أو إغلاقاً شاملاً. لا تعدّل `docs/audit/findings.csv` أو أدلة التدقيق التاريخية حتى تطابق الواقع ظاهرياً؛ أضف سجلاً مستقلاً للحالة الجديدة واربطه بالمصدر.

## 2. تحقق أولاً من الإمكانية والأثر

- استعد الحزم وابنِ الحل من Visual Studio أو باستخدام MSBuild المتوفر على جهاز Windows، شخّص أخطاء التجميع والتحذيرات المؤثرة وأصلحها بأقل تعديل صحيح، ثم أعد البناء. شخّص مراجع DLL الخارجية بدلاً من حذفها لإسكات الأخطاء.
- شغّل كل برامج `tests/repair/*.py` وفحص `python docs/repairs/tools/build_status_archive.py --check` إن كان Python متاحاً، وسجّل أسماء الفاشلة ومخرجاتها. هذه الحاضنات غالباً شواهد مصدر ونماذج، **لا تنفذ C# أو WPF أو SQL Server**؛ أضف اختبارات C# وتشغيلية فعلية، ولا تعدّل اختبارات قائمة لمجرد تمريرها.
- تحقّق من اختبارات التدقيق على خط الأساس الذي صُممت له منفصلاً عن فرع الإصلاح: أدوات B39R1 تثبّت بصمات ومقتطفات المصدر الأصلي، وقد تفشل في فرع الإصلاح بسبب تغيره وغياب ملفات build القديمة. لا تعالج ذلك بتغيير الأدلة أو استبعاد الفشل؛ أنشئ اختباراً حديثاً مستقلاً للشيفرة الحالية. اقرأ `docs/repairs/SYNC.md` لنتيجة الدمج الحالية.
- اعمل مصفوفة تتبع لكل إصلاح R-001..R-263 والحواجز H في `TRACKER.md`: رقم الإصلاح والنتائج، المتطلبات، المسارات والمتصلون، الدليل، الاختبارات على Windows، النتيجة (ناجح/فشل/محجوب/لم يختبر)، والمخاطر. لا تكتفِ بقراءة كل بطاقة: اختبر كل مسار بقدر توفر البيئة، مع تغطية النجاح والفشل والإلغاء والتزامن والبيانات التاريخية. راجع أيضاً الإصلاحات/الحواجز الأحدث إن وُجدت.

## 3. الأولويات والمتبقي

ابدأ بالأخطر مالياً وأمنياً وراجع حالات الفشل المفتوحة، ومنها:

1. سلامة الفواتير والمرتجعات وهويات GlobalID والفرع، بما فيها **P7-164 وP7-165**؛ قارن عقد الكاتب والقارئ والمخطط الفعلي ولا تخلط معرفاً نصياً بمعرف رقمي. لا تعتبر خطأ الاستعلام «لا يوجد مرتجع». اختبر التكرار والتزامن عبر فرعين والاستثناءات وإعادة المحاولة.
2. القيود والسندات والإشعارات، وحدة المعاملات والـrollback وغموض commit والمزامنة ومصالحة البيانات التاريخية وتفويض المستخدم. حراس وتعطيلات السندات القديمة والجرد والرواتب وإغلاق الوردية مقصودة لحماية البيانات وليست حلولاً مكتملة؛ **لا ترفع الحظر** إلا بعد إثبات البديل والمخطط والمصالحة والاختبار وموافقة المالك عند الحاجة.
3. تقارير المزامنة **P7-167** والقوالب المتاحة وأعداد الصفوف، و**P7-166** للنجاح دون تصدير، وامتدادات P7-050 وP1-033. قارِن صيغة الملفات المعلنة بالبايتات والحقول المطبوعة بالقالب وبالبيانات المعروضة. تحقق من امتداد P7-160 مقابل R-087 الحالية قبل أي تعديل مكرر.
4. الضريبة والخصومات والسعر الشامل وإشارة المرتجعات والتقريب والعملات والرواتب؛ لا تخمّن سياسة مالية أو تغير نسبة افتراضية دون مصدر موثوق واعتماد المالك. اختبر أمثلة حسابية وسجلات مطابقة وقيود دفتر الأستاذ.
5. المخزون وحركة المواد والهويات بين الفروع وحوارات الخصائص والإلغاء، خصوصاً **P7-151**؛ افحص ملكية الصف وتدفق الإلغاء وكل المستدعين قبل تغيير التوقيع. اختبر عدم حفظ تعديل جزئي عند إلغاء الحوار.
6. الأمان: التفويض على مستوى العمليات والخادم وليس إخفاء أزرار فحسب؛ SQL بمعلمات، وإدارة الأسرار، وحدود الفروع، ومسارات الملفات والمزامنة، واختبارات منع الوصول للمستخدم غير المصرح به.

لكل مشكلة: أعد إنتاجها أو أثبتها على المصدر الحالي، افهم العقد والمستدعين والبيانات قبل التغيير، أصلح السبب الجذري دون تعطيل عملية سليمة بلا مبرر، أضف اختباراً يفشل قبل الإصلاح وينجح بعده متى أمكن، ثم شغّل الاختبارات والبناء ذات الصلة. إذا توقفت على عقد أو قرار مالي أو مكتبة/قالب/بيانات، وثّق العائق وسؤالاً محدداً للمالك، وانتقل لعمل مستقل بدلاً من التخمين.

## 4. مخرجات مطلوبة

- حدّث سجل متابعة منفصلاً مع ربط كل تغيير ونتيجة بالمصدر الحالي، وأسماء الاختبارات ومخرجاتها، وما بقي مفتوحاً وتبعياته. حافظ على بقاء البيانات التاريخية وقرارات المالك واضحة؛ حدّث الأرشيف المشتق فقط عبر أداته بعد مراجعة قواعده.
- أعطِ تقريراً دورياً مختصراً عن التقدم، ولا تطلب مني الاختيار عند قرارات هندسية واضحة ومنخفضة المخاطر؛ اسأل فقط عند الحاجة إلى صلاحية أو قرار أعمال أو بيانات غير متاحة.
- في نهاية الجلسة اذكر: ما بُني واختُبر فعلياً، ما أصلحته والملفات والاختبارات، ما فشل أو تعذر، العوائق وأثر التعطيلات، ونقطة الاستئناف التالية. لا تقل إن التطبيق جاهز للإنتاج أو إن جميع الإصلاحات صحيحة ما لم تثبت اختبارات البناء وWPF وSQL والقبول المالي ذلك.
- لا ترفع أو تدمج أو تنشر على GitHub من جهاز المستخدم دون موافقته الصريحة؛ حافظ على تغييرات المستخدم وأظهر حالة Git.

ابدأ الآن بفحص البيئة والسجلات وبناء الحل، ثم نفّذ العمل على دفعات متتالية.
