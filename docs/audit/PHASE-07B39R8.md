## 4. الإدراج المرتبط: الإلغاء لا يعني التراجع

1. **القارئ بالمرجع يسبق قبول البنود.** المساعدان يحرسان رجوع المنتقي الأول، ثم BindingInvoice(ref الأب) قبل نافذة البنود الثانية. إلغاء الطفل يعيد حقله، لا snapshot للأب أو rollback للقارئ السابق. جميع المتصلين11 يتلقون void ويتابعون كتابات مختلفة؛ دعم إضافي لحد **P7-160** دون تغيير جذره/حالة معالجته.
2. **رفض «جديد» في المشتريات لا ينتقل إلى المتصل الخارجي.** CheckBeforeClear يستطيع إيقاف void btnNew، لكن btnInsertLinkedInv يستمر إلى أذرعه الأربعة. بقي السؤال غير مرقّم ومقارنًا بـP7-159، لا دمجًا قسريًا معه.
3. **POS يمسح قبل كلمة المرور.** رفض التنبيه يسبقCLR ويعود، أما رفض كلمة المرور فيأتي بعده. لا يُساوى المساران ولا يُسند إلغاء void إلى نجاح/فشل موحد.
4. **الصحة ليست non-null.** القارئان قد يضعان ref=null عند غياب الرأس/الفشل العام، أو يتجاوزان صفوفًا بعد كتابات سابقة؛ المساعد يبتلع أخطاء ثم قد يستمر الأب. دعم **P7-161** دون تشغيل SQL/provider أو ادعاء ترطيب/حفظ كامل.
5. **هدف بنود العقد مختلف.** المساعد يملأ child.invcontract، لكن كاتب البنود المختارة وحاذفها يستعملان child.inv. استعلام23 لا يعيد توجيه الكاتب، وفرع نتيجة مساعد العقد فارغ. تفصيل للسؤال المحمول R6C-CONTRACT-RESULT، لا دمج مع P7-144 الخاصة باستيراد آخر بند.
6. **هوية السطر ليست ItemId وحده.** الاختيار يغير كل البنود المطابقة للصنف ويحذف بمجموعته، دون هوية وحدة/مخزن/سطر. «الكل» يسلك مسارًا آخر. بقي سؤالًا غير مرقّم؛ لا افتراض defaults/deep-copy/aliasing خارجي أو فساد مالي مرصود.
7. **السنة ومخارج الحوار مختلفة.** البيع/العقد قد يبدلان العامة قبلCLR/المنتقي بلا finally. زر البحث/Escape، وزرا البنود المحدد/الكل والإلغاء لا يستعيدون السلسلة/العلم بالطريقة نفسها. يُحمل سؤال R6 مع تفصيل مسند، لا يُغلق من إرجاع الطفل.
