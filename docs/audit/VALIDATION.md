# سجل الفحص والتحقق — المرحلة الأولى

**التاريخ:** 2026-11-16 — **مرجع المصدر:** `10ba215152f722c8808aea0bb672c1d1d4d9d711`.

## 1. حدود بيئة الفحص

- البيئة المتاحة: Linux x86_64، Python 3.11.2 وGit 2.39.5.
- `dotnet --info`: تعذر التنفيذ، `command not found`، exit code 127. لا يتوفر `msbuild` أو `mono/csc` أيضاً.
- التطبيقان يستهدفان `net8.0-windows` وWPF؛ لا توجد هنا بيئة تشغيل Windows أو SQL Server اختباري أو أجهزة الدفع والطباعة.
- لم تُستعد الحزم أو يُجر build/test للتطبيق. لم تُستخدم الثنائيات القديمة لإثبات بناء المصدر.
- لم تنفذ SQL أو ترقية أو تحقق كلمة مرور حية، ولم تُختبر خوادم broker/FTP/API أو تُنزّل حزمة إصدار.
- ملفات `.resx` قُرئت XML/نصاً لا عبر deserialization للكائنات المضمّنة. ملفات EXE/DLL حُصرت وبُصمت فقط، ولم تُشغّل.

**النتيجة:** الفحوص التالية أدلة ساكنة، وليست نجاح اختبارات C# أو شهادة أمن/صحة مالية. «محجوب» لا يعني «ناجح» ولا «فاشل بالمترجم».

## 3. إعادة الفحص المحلي الآمن

من جذر المستودع:

```bash
# قراءة المشروع وطباعة ملخص دون تعديل ملفات
python3 docs/audit/tools/collect_baseline.py

# التحقق من أن الملفات الأصلية تطابق بصمات لقطة المرحلة الأولى
python3 docs/audit/tools/collect_baseline.py --verify
```

- يعمل السكربت بمكتبة Python القياسية وGit فقط؛ لا شبكة أو SQL أو تحميل assembly أو استدعاء للتطبيق.
- ينظر إلى الملفات المتتبعة داخل شجرتي المشروع والحل؛ لا يحوّل المستندات الجديدة إلى أرقام تغطية للمشروع الأصلي.
- `--verify` يعيد 1 إذا اختلفت قائمة ملفات المشروع المتتبعة أو بصماتها. لا يشمل ملفات تشغيل غير متتبعة أضيفت خارج Git؛ لذلك ليس فاحص أسرار/ملفات تشغيل شاملاً.
- `--write` يجدد `evidence/baseline.json` و`evidence/inventory.csv` فقط، ولا يصلح الشيفرة. يجب حفظ مرجع الأدلة السابقة قبل استعماله بعد إصلاحات.
- `review-scope.csv` وصف بشري للنطاق، لا حساب لتغطية تنفيذية. `scoped-static-review` لا تعني مراجعة كل سطر في الملف، و`inventory-only` لا تعني أنه سليم.

### قيود أمان مهمة للتنفيذ المستقبلي

1. لا تُجرّب P1-007 أو سكربتات `.resx` أو الاستعادة أو قتل العمليات على جهاز/SQL مشترك أو إنتاج.
2. بيانات اصطناعية واعتمادات غير حقيقية في fixtures والسجلات؛ لا يُدرج secret حقيقي في command line أو لقطات أو ملفات نتائج.
3. الحصول على موافقة منفصلة قبل أي اتصال خارجي أو تشغيل migration أو اختبار دفع، حتى لو كان اختباراً معتمداً في هذه الخطة.
4. إثبات backup وخطة استعادة قبل اختبار الفشل. اختبارات انقطاع القرص/العملية للتثبيت المؤقت فقط.
5. الاحتفاظ بلقطة source/build/package/schema، ومدخلات ونتائج وأوامر الاختبار المنزوعة الأسرار لربط الإغلاق بمعرف النتيجة.

## 5. متى تُعتبر نتيجة مغلقة؟

- تعديل محدد ومراجع، لا تغيير عام غير مرتبط بالدليل.
- اختبار قبول مناسب من الجدول أو بديل موثق يشمل فرع الفشل، مع بيئة وإصدار المصدر.
- بيان أثر الترحيل والتوافق مع العملاء والقواعد القديمة وخطة الرجوع عند الحاجة.
- تحديث حالة النتيجة بالدليل؛ وإبقاء المخاطر التجارية/الخارجية غير المحسومة معلقة.

**الوضع الآن:** لا نتيجة مغلقة، ولا اختبار تشغيلي للتطبيق منفذ. سلامة XML أو مطابقة SHA-256 ليست علاجاً لأي من الأخطاء المسجلة.
