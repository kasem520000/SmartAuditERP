## 1. حدود التنفيذ

- استمرت المراجعة على Linux؛ لا `dotnet` أو MSBuild أو Mono/مترجم C# متاح في البيئة. لم يُبنَ التطبيق أو تُستعد اعتمادياته.
- لا Windows/WPF أو SQL Server اختباري أو backend/broker sandbox أو شهادات SQL تجريبية متاحة لهذا العمل.
- **صفر اختبارات تطبيق/استغلال/شبكة/SQL/استعادة منفذة في المرحلة الثانية**. لا تشغيل EXE/DLL أو تحميلها أو تفكيك كائنات الموارد المتسلسلة.
- الأدوات المنفذة Python/Git وبحث نصي وقراءة source/XML فقط؛ لا اتصال خارجي أو تغيير كلمات/منح/بيانات.
- كل نتائج الشيفرة ما زالت `open-not-remediated`؛ كل سيناريوهات القبول أدناه **`not-executed`**. لا نتيجة «نجاح» أو «فشل تشغيل» مستنتجة من القراءة الساكنة.

## 4. شروط الأمان لأي اختبار لاحق

هذه الشروط **ليست إذناً بالاختبار**؛ يلزم تفويض منفصل وبيئة مناسبة عند التنفيذ:

1. بناء Windows من المصدر المعلوم بعد معالجة متطلبات الاعتماديات والترخيص. لا تشغيل الثنائيات المتتبعة كبديل عن build موثوق.
2. SQL معزول وبيانات اصطناعية قابلة لإعادة الإنشاء؛ حساب اختبار أقل صلاحية؛ نسخ/restore مثبتة قبل تجارب تدميرية مأذون بها. لا إنتاج أو خادم مشترك.
3. تبدأ الاختبارات باعتراض الأوامر والملفات والعمليات والنشر الخارجي. لا تسمح اختبارياً لتهيئة logins/`sysadmin`/`sa` أو RESTORE/TRUNCATE بالخروج إلى خادم بسبب مسار جانبي.
4. API/broker/وقت وProcess/FileSystem بدائل وهمية أولاً. لا دفع/طباعة/تحديث/إرسال تذكرة أو مرفق حقيقي. لا نداء خادم مزود دون sandbox وإذن منفصل.
5. لا كلمات/مفاتيح/توكنات أو بيانات عملاء في ملفات النتائج أو سطر الأوامر أو الدردشة. تعطيل نشر التعريفات/المزامنة في fixtures دون تعطيل الحارس المراد اختباره.
6. اختبار المسار/النوع لا يشغّل EXE مجهولاً ولا يحذف ملفاً خارج جذر مؤقت. استعمل stubs للعمليات الخطرة وسجل قرار الرفض فقط.
7. مدخلات SQL أولية حميدة مثل اسم اصطناعي يحوي apostrophe وUnicode؛ أسماء/مسارات DDL تسجل دون تنفيذ. لا حاجة إلى payload هجومي لإثبات وجوب parameters.
8. وثق commit/package/schema/provider/OS والمستخدم/الدور/الفرع والموارد والتوقع والنتيجة الفعلية وآثار القاعدة/الملفات بعد كل تجربة، مع مسح الأسرار. لا تعلن إصلاحاً لاختفاء الزر وحده.

## 6. تحويل نتيجة إلى مغلقة لاحقاً

- إصلاح محدد ومراجع في الفرع المعتمد، مع خطة انتقال للأسرار/المخطط/المنح والعملاء القدامى عند اللزوم.
- تنفيذ حالة قبول مناسبة أو بديل موثق، بفروع النجاح والرفض والفشل؛ أثر DB/ملفات متوقع، لا رسالة «نجح» من UI فقط.
- تحقق من طبقة الثقة المعنية: رفض UI لا يثبت رفض API/SQL، وparameter لا يثبت authz، وTLS لا يثبت ownership.
- إدراج البيئة والأدلة المنزوعة الأسرار والقيود المتبقية، ثم تغيير status في findings.csv بدليل. **كل ذلك لم يحدث هنا.**
