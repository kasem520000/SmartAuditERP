## 2. الأدوات والآثار القابلة للإعادة

```bash
python3 docs/audit/tools/collect_baseline.py --verify

python3 docs/audit/tools/validate_audit.py
```

- الأول لا يشغل ERP؛ يقارن اللقطة التاريخية ويعيد الحصر/الفحص الشكلي. **لا تستعمل --write لتحديث baseline/inventory خلال مقارنة هذه النسخة**.
- الثاني يحسب illustrations يدوية فقط بـDecimal/boolean/list. لا imports لتطبيق، أو تحميلAuditorAPI أو WPF، أو محاكاة مزود SQL. المتغيرات/الفروع/المعادلات منسوخة يدوياً؛ احتمال خطأ النقل وحدود المثال معلنان في كل سجل.
- الثالث محدث للمرحلة3؛ يتحقق أيضاً من أن JSON الأمثلة يطابق إعادة حساب الأداة الآمنة. لا يثبت اتساق المعنى المحاسبي لكل citation ولا صحة trace بسبب وقوع أسطره ضمن الملف فقط.
- نتيجة آخر فحص توثيقي في [checks-03.json](evidence/checks-03.json)؛ عدد references يتضمن التكرار بين CSV/MD وليس عدد أسطر/ملفات تمت تغطيتها بالتنفيذ. السجل لا يحاول hash نفسه.
- الأمثلة في [arithmetic-witnesses-03.json](evidence/arithmetic-witnesses-03.json)، والمولد في [check_financial_witnesses.py](tools/check_financial_witnesses.py). نجاح assertion يعني اتساق المثال حسابياً، **لا أن النظام اجتاز/فشل اختباراً منفذاً**.

لإعادة فحص دليل المرحلتين التاريخيتين بعد زيادة السجل، دون الرجوع إلى سجل74 أو الكتابة فوق checks-02:

```bash

```

هذا الوضع يقرأ [findings-through-02.csv](evidence/findings-through-02.csv) والتقارير/النطاقات التاريخية، لا نسخة قديمة من التطبيق أو طلب صلاحية جديد. قد يختلف عدّ references في مخرجه عن616 التاريخية بسبب اتساق أداة التحقق المحدثة؛ **checks-02.json هو الأثر التاريخي كما سلم**. بصمات14 artifact ولقطة السجل موثقة في [provenance-03.json](evidence/provenance-03.json). لا يُعاد توصيف إخفاق تشغيل لاحق كنجاح تاريخي أو العكس.

## 4. متطلبات وأمان تنفيذ خطط القبول لاحقاً

1. **تفويض جديد للتشغيل وبيئة اختبار معزولة**، لا تنفيذ قبول ضمن هذه المرحلة لمجرد توفر SQL في مكان آخر. يمنع الاتصال بالإنتاج أو تشغيل التدوير/الترحيل على قاعدة عمل.
2. بناء Windows نظيف من المصدر واعتماديات موثوقة معلومة الإصدار، مع DevExpress/.NET/SQL/provider وDTOs وسياسة ترخيص مناسبة. لا تحميل ثنائيات غير موثوقة لإكمال فحص ساكن.
3. SQL اصطناعي أو نسخة مجهلة مأذونة وsnapshot/restore مثبت، logins محدودة، مقارنة للمخطط المرفق مقابل مخطط الاختبار، وتوثيق أي defaults/triggers إضافية. نسخة النشر الحقيقية لا ترسل في الدردشة.
4. قطع الشبكة وتعطيل MQTT/API والضريبة/المدفوعات/البريد/الدعم والنسخ الخارجي؛ استعمال adapters وهمية للطباعة وProcess/FileSystem إن لزم. لا ضغط تجريبي على مزود أو خصم بنكي.
5. مرجع محاسب لسياسة الفترة والضريبة والعملات/التقريب والشيك والمخزون والإلغاء وتاريخ posted entries؛ توثيق نتيجة كل fixture قبل تنفيذ البرنامج. الخلاف التجاري يبقى blocked لا fail مُختلقاً.
6. نقاط fault injection مسماة قبل/بعد كل كتابة/commit، وحواجز جدولة لجلسات التزامن بدل «نقر متقارب» لا يثبت مسار السباق. فشل بعدcommit أو فقد رد لا يعني أن العملية لم تعتمد.
7. تقييم الصفوف والهويات والروابط والمجاميع قبل/بعد. لا تعتمد الرسالة أو bool أو عدد records فقط؛ يجب مطابقة الرأس والبنود والدفتر وإشارات الإلغاء والتاريخ. احفظ السبب والActor وSubject دون أسرار.
8. معايير تصحيح البيانات منفصلة: كشف فروق، اعتماد نطاق/سبب، معاينة، backup/rollback ومراجعة، ثم إعادة قبول. لا إصلاح تلقائي لكل قيد مختلف أو إعادة توليد شاملة.

حالات الخطة الآن `not-executed` كلها. عند التفويض قد تصبح blocked بالمتطلبات، ثم passed/failed فقط مع دليل فعلي؛ لا تغير الحالة بناء على source reasoning أو illustration.

## 6. تفسير حالات الفشل المقترحة

- P3T-05/06/07: نريد إثبات وحدة الاعتماد بآثار جداول فعلية. أن يقوم Close/Dispose بrollback لمعاملة رأس لا يبرهن تراجع قيد اعتمد بمعاملة أخرى.
- P3T-09: يجب جدولة حالتين: فحصا غياب متزامنان قد يؤديان إلى PK conflict، وA يعتمد قبل فحصB فيفسره upsert كتعديل. لا تفرض الخطة أن كل سباق كتابة فوق السابق.
- P3T-13 إلىP3T-16: استخدم fixture لسند قائم له رابط صحيح عند اختبار التعديل/الحذف، حتى لو كان إنشاء Q/VAT الجديد محجوباً بخطأ NOT NULL. الفشل السابق لا يلغي عيب مسار لاحق مستقل.
- P3T-17/18: تحقق من تفاصيل Entry قبل الحفظ ثم من المخزن؛ إصلاح رسالة التوازن أو تقريب الإجمالي لا يصلح اتجاه الضريبة أو صافي البنك.
- P3T-21: تحقق من صفوف EmpSalaryAddSub والSubject لا من «نجح الإغلاق»؛ أثر مسير الراتب وتوقيت الخصم يتبعان سياسة ومراجعة المرحلة7.
- P3T-24 إلىP3T-28: قارن cutoff ومجموعة الفروع/الحالة أولاً، ثم التفاصيل/المجاميع/البطاقات. لا تجعل اختلاف query أو توسعة شجرة مصدراً لمرجع مستقل متناقض.
- P3T-29: dry-run mapping وbackup/restore ومفاتيح محلية مكررة بين فروع شرط أساسي. **لم ينفذ الترحيل أو يعاد إنتاج تلف**؛ لا يجوز تفسير خطة هذا الاختبار كتعليمات تشغيل على قاعدة حالية.
- P3T-32/33/34/35: بعضها يختبر متطلباً/سياسة أو مطابقة غير محسومة، لا ثغرة مستقلة. ولا يقرر اكتمال المبيعات/المخزون/المزامنة قبل مراحلها.
