### P7-128 — تفاصيل الضريبة تورث علم IsVAT بين طلبات المشتريات بلا بنود فتسقط صفوفاً خاضعة

**Medium / confirmed / implementation-defect / open-not-remediated / next_phase=8.** تأكيد علة مصدر محلية عند تحقق المدخلات، لا وقوع خطأ إنتاج أو تقدير خسارة أو إذن إصلاح.

**سلسلة السبب:** `IsVAT` حقل نافذة يبدأ true مرة. `ShowInvs` يمسح الصفوف ويعيد المجاميع، لكنهما لا يعيدان العلم. يستدعي main-loop أولاً `ProcessInvoiceRow`؛ إذا خلا subTable يعود قبل `IsVAT=true`. بعد ذلك يستدعي للمشتريات مسار no-sub الذي يختار صراحة رؤوساً بلا Inv_Sub. هذا المسار يصفر المبالغ لكل صف، لكنه لا يعيد العلم true؛ يكتب false عند tax0 فقط. فرع tax>0 يملأ المبالغ، ثم يصل إلى `if (!IsVAT && rbWithVAT.IsChecked == true) continue;` فيسقط الصف بحسب علم طلب سابق.

**عينة مستقلة مشروطة، بلا تشغيل:** نافذة مشتريات واحدة، قراءة ناجحة، لا سندات أو بنود مفصلة تغير الحالة، فرع/فترة مؤهلان وثقافة ومعدل lookup متوافقان. عرض Z tax0 في وضع بدون ضريبة يترك العلم false. إعادة العرض الفعلية لطلب with-VAT يحوي T tax15 بلا بنود تُعيد main مبكراً ثم يستبعد no-sub الصف T. نافذة جديدة تنفذ **نفس الطلب الأخير ونفس الصفوف** بعلم true فتدرج T. لا يحتاج الفرق فشل SQL أو طباعة لقطة قديمة؛ المصدران نجحا والعرض جديد.

**امتداد السببية داخل الطلب نفسه:** no-VAT مع ترتيب Z tax0 ثم T tax15 قد يمرر T بعد أن جعل Z العلم false، بينما يعكس الترتيب نتيجته. هذا مظهر لنفس غياب reset/التصنيف المحلي، لا نتيجة ثانية. النموذج يتتبع **أهلية الصف فقط**؛ لا يدعي صحة المبالغ الافتراضية المصفرة أو إعادة حساب معادلة VAT كلها.

**شواهد مقابلة:** with-VAT البارد يدرج T؛ مرور main-row ذي subTable غير فارغ يعيد العلم true. ووجود tax0 ضمن with-VAT البارد لا يضع false وحده لأن فرع with لا يكتبه. لذلك لا نزعم أن كل طلب أو كل فاتورة أو كل parent يصاب، ولا نفترض أن كل بيانات النشر تتضمن رؤوساًبلا بنود.
